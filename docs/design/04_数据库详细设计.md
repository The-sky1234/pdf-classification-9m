# 04 数据库详细设计（PostgreSQL，Planner，设计不执行迁移）

依据：`docs/需求整理V3.md`、`docs/design/01_系统总体架构设计.md`、`docs/design/05_接口详细设计.md`、`contracts/phase1/*`、`backend/models.py`、`backend/registry.py`、`backend/store.py`、`scheduler/queue.py`、`scheduler/archive_worker.py`、`migrations/001_init.sql`。审查修订：2026-10-10。身份规则冻结：2026-10-10。差异：旧库只有 `doc_tasks` 与 `classification_results`；V3 目标仍是下面 10 张表。第 2b 表只记录源字节版本，不占这 10 张表的编号，后面的表号不顺延。旧 `IRRELEVANT` 只做读兼容，不批量变成已批准的 LV04。旧 25 类不能直接当成 27 场景归档。

`file_id` 标识一份源文件，`task_id` 标识该文件在某一阶段的当前执行行。二者在新登记中各用各的 UUIDv7，禁止互相当值。已经写入 `doc_tasks` 的旧行除外，见下文「历史数据」。`source_sha256` 只表示文件字节哈希，可空，不是登记键。

本轮核对过的实现事实：`backend/registry.py` 用 `str(uuid5(NAMESPACE_URL, "file:"+路径))`，得到带连字符的 36 字符；`backend/store.py` 的 `create_task` 用 `uuid5(NAMESPACE_URL, 路径+":"+路径字符串 SHA-256 的前 32 位).hex`，得到不带连字符的 32 位小写十六进制。两套输入不同，字符串形态也不同。`contracts/phase1/data-contract.md` 只写了 `file_iduuid5`，没有冻结输入串。`scheduler/queue.py` 把 `task_id` 放进 `seen` 后永久拒绝再次入队。`scheduler/archive_worker.py` 的 `uuid4` 只用于临时文件名 `.part-{hex}`，不分配 `file_id`。这些都不是下文的生成规则。

追踪链：`file_registry.file_id` → `processing_tasks(file_id, task_id)` → 去重和解析（`file_id`）→ 排除、分类、`archive_decisions(file_id, version)` → `archive_executions(decision_id)` → `review_records(from_version → to_version)`。按 `file_id` 加决策 `version` 可以看完一轮决策。`batch_id` 用来反查整批。第 6、7、9 表的 `version` 对齐同一轮决策，以第 9 表的 `version` 为准；第 6、7 表没有行时不补假版本。第 10 表 `decision_id` 外键指向第 9 表。第 3 表 `task_id` 为主键。同一文件同一阶段只保留一行当前任务。第 2b 表的 `content_version` 是源字节版本，与第 6、7、9 表的决策 `version` 不是同一条序列，互不代替。

## 文件身份规则（已冻结）

本节是新登记的规范。第 1、2、2b、3、4 表的约束实现本节。近重复相似度、归档文件名算法、非 UTF-8 文件名将来是否改收，仍按需求第 10 节和第 6 节留在原 TBD，本节不写数字。

### 最终推荐：新 file_id 与新 task_id 都用 UUIDv7

新的 `file_id` 和新的 `task_id` 只用 RFC 9562 UUIDv7。生成输入不含路径、不含哈希、不含 `NAMESPACE_URL`。`file_id` 只在某条规范路径第一次成功插入 `file_registry` 时留下一枚。`task_id` 只在某个 `file_id` 的某个 `stage` 第一次成功插入 `processing_tasks` 时留下一枚。幂等靠唯一约束，不靠把路径算进 ID。

同一进程内的生成步骤：

1. 取 Unix 纪元毫秒，写成 48 位大端整数。若小于本进程上一枚已发出的时间戳，就等到时钟追上后再取。
2. 与上一枚同一毫秒时，把 12 位 `rand_a` 计数加 1。计数将超过 4095 时，等到下一毫秒并把计数归零。
3. 版本半字节固定为 `7`。变体两位固定为 `10`。其余 62 位来自密码学随机数。同一毫秒内只要计数递增，规范字符串就必须严格按字典序变大；其余随机位可以保持或重抽。
4. 格式化成下文的规范字符串后再插入。插入冲突若来自 `source_path`，这枚新 ID 直接丢弃。插入冲突若来自主键且路径不同，整段事务回滚，再生成另一枚 UUIDv7。禁止把已经属于别的路径的 `file_id` 拿来用。

否决 UUIDv4：它没有时间序。约 900 万行按主键插入时，随机键的 B 树局部性更差。它也不能判断“这条路径是不是已经登记过”。

否决用数据库自增整数做 `file_id` 或 `task_id`：导入、导出和队列消息会把序列值当成跨模块身份，也和现有以 UUID 文本传递的任务消息不是同一种键。第 1 表的 `id SERIAL` 继续只做批次代理键，可以出现在批次行和 `batch_id` 外键里，不得当作 `file_id`。

否决继续用现有两套 UUIDv5：

- 契约没有冻结输入串，不能从“写了 uuid5”推出唯一算法。
- `registry.py` 的输入是 `"file:"+路径`，`str(uuid)` 带连字符。`store.create_task` 的输入是 `路径+":"+路径哈希前 32 位`，`.hex` 不带连字符。同一路径会算出两个值。
- 路径规范化一旦改变，由路径派生的 UUIDv5 会整批改变，已经发出的身份跟着变。
- `create_task` 把路径哈希绑进 `task_id`。文件身份和内容身份被绑在一起，而这条哈希还不是文件字节哈希。内容变化时应保持 `file_id`，UUIDv5 路径派生做不到“只在首次插入时生成一次”。

字节格式：

| 项 | 新 `file_id`、新 `task_id` |
|---|---|
| 位数 | 128 位，RFC 9562 UUIDv7 |
| PostgreSQL 类型 | `TEXT`（物理上可用 `VARCHAR(n)`，`n>=36`）。禁止用 PostgreSQL `UUID` 类型，禁止用 `INTEGER` / `SERIAL` |
| 规范字符串 | 36 字符，小写十六进制，8-4-4-4-12，带连字符。无大括号，无 `urn:uuid:` 前缀 |
| 形态检查 | `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` |
| 读出 | 返回写入时的原文。禁止在读出时补连字符、删连字符或改大小写 |

不用 PostgreSQL `UUID` 类型，是因为该类型读出时总会变成带连字符的文本，旧的 32 位十六进制会在同一列里被改写。旧值必须原样留在列里。

应用在插入前生成 ID。不调用 `uuid.uuid5`、`uuid.uuid4`、`uuid.uuid1`，也不调用 `gen_random_uuid()` 或数据库的 `uuidv7()`。这样，路径冲突时可以证明被丢弃的那枚 ID 没有落库。

### 五个身份字段

| 字段 | 含义 | 谁生成 | 唯一性 | 能否更新 |
|---|---|---|---|---|
| `file_id` | 一份源 PDF 的稳定身份，绑定规范路径，不绑定字节内容 | Registry。只在该规范路径第一次插入成功时留下一枚 UUIDv7 | `file_registry` 主键 | 否 |
| `task_id` | 该 `file_id` 在某个 `stage` 上的当前执行行 | 第一次插入该 `(file_id, stage)` 时生成一枚新的 UUIDv7。`SCAN` 由 Backend 生成，其他阶段由 Scheduler 生成 | `processing_tasks` 主键；另有 `UNIQUE(file_id, stage)` | `task_id` 本身否。失败重试和内容升版都改同一行的状态列 |
| `batch_id` | 扫描批次代理键，等于第 1 表 `id` | 数据库 `SERIAL` | 第 1 表主键 | 主键否。`file_registry.batch_id` 只记首次登记的批次，之后不改 |
| `source_path` | 规范化后的绝对路径 | Registry 按下一节写入 | 约束名 `uq_file_registry_source_path` | 否 |
| `source_sha256` | 文件原始字节的 SHA-256，64 位小写十六进制 | Parser 计算字节后，经第 2b 节的事务写入 | 可空，非唯一。只有普通索引 `ix_file_registry_source_sha256` | 仅按第 2b 节：从 NULL 写成首次确认的哈希，或在 `content_version` 加 1 时改成新哈希。禁止改回 NULL，禁止写入路径哈希 |

`id_origin` 与 `task_origin` 只有 `LEGACY` 和 `V7` 两个值，插入时写定，之后不改。新扫描只写 `V7`。

### 规范路径与幂等登记

生产环境是一台 Linux，路径区分大小写。规范化按下面的顺序做，测试按这一顺序断言。

1. 拒绝非文本、空串、含有 U+0000 的路径。
2. 路径中若含代理码位 U+DC80–U+DCFF，视为当前不能按 UTF-8 文件名登记：不生成 `file_id`。将来是否接受原始字节文件名仍 TBD，在放开前就按这一拒绝执行。
3. 保留大小写，也不做 Unicode NFC/NFD 正规化。两个不同的码点序列就是两个路径。不把 `\` 换成 `/`。Linux 上反斜杠只是文件名里的普通字符。
4. 必须以 `/` 开头。相对路径直接拒绝，不拼接进程当前目录。
5. 只用 POSIX `normpath`：合并重复的 `/`，消去 `.` 与 `..`，去掉末尾的 `/`。不调用 `realpath`、`readlink`，也不跟随符号链接。
6. 结果若是 `/`，或者仍以 `/` 结尾，拒绝。
7. 源根来自本批次 `source_roots`。每个源根先按步骤 3–5 规范化，源根本身不能是 `/`。文件路径必须带有某个源根 `R` 的前缀 `R + "/"`。`/data/pdfs` 不覆盖 `/data/pdfs2/a.pdf`。
8. 对步骤 5 的结果做 `lstat`。若是符号链接，拒绝，不跟随，不用链接目标当 `source_path`。目录遍历也不跟随目录符号链接。
9. 步骤 1–7 已通过但 `lstat` 失败：单独提交批次状态，`scan_status='FAILED'`，`last_error` 记下该路径，游标不动，不插入 `file_registry`。续跑会再次尝试这条路径。
10. 通过全部检查的字符串才是 `source_path`。

步骤 2、7、8 的拒绝不插入 `file_registry`。其中，词法结果仍在某个源根之下的拒绝（符号链接、不能按 UTF-8 登记的名字）把游标推进到该词法路径，并把 `skipped_count` 加 1。逃出源根的路径不写入游标，避免一个源根外的字符串把游标推过尚未扫描的合法路径。

同一规范路径的插入：

```sql
INSERT INTO file_registry (
  file_id, source_path, source_sha256, "bytes", mtime,
  batch_id, content_version, id_origin, created_at
) VALUES (
  :file_id, :canon, NULL, :bytes, :mtime,
  :batch_id, NULL, 'V7', now()
)
ON CONFLICT ON CONSTRAINT uq_file_registry_source_path DO NOTHING;
```

随后在同一事务里按 `source_path = :canon` 读回 `file_id`。

- 插入影响行数为 1：本枚 UUIDv7 就是该行的 `file_id`。同一事务插入 `processing_tasks`：`stage='SCAN'`，`status='PENDING'`，`retry=0`，`content_version` 为空，`task_origin='V7'`，`task_id` 是另一枚 UUIDv7，且不等于 `file_id`。
- 插入影响行数为 0：丢弃本枚尚未落库的 UUIDv7。读回已有 `file_id`。已有 `SCAN` 行则读回它的 `task_id`，不改 `status`、`retry`、`task_id`、`batch_id`。没有 `SCAN` 行时才插入一行，新 `task_id` 仍是 UUIDv7，`task_origin='V7'`，并且不等于 `file_id`，包括旧 `file_id` 仍是 32 位十六进制的情况。
- 两个事务同时插入同一规范路径：成功插入的那一行留下它的 `file_id`。另一个事务只读回这一枚。表里只有一行。

`bytes` 与 `mtime` 在首次插入时取当时的 `lstat` 结果。此时 `source_sha256` 仍为空，还没有内容版本。`mtime` 以 UTC `timestamptz` 保存，比较精度到微秒。

### 批次游标、续跑与重复消息

登记幂等只靠 `uq_file_registry_source_path` 和 `uq_processing_tasks_file_stage`。登记事务不读、不写 Redis 的 `seen`。`scheduler/queue.py` 里同一 `task_id` 一旦进入 `seen` 就永久拒绝再入队，这是当前实现缺口，不是身份规则。队列丢失或 `seen` 误挡之后，按 `processing_tasks.status='PENDING'` 重新投递，不为了入队再插入第二个 `file_id`。

同一 `batch_no` 同一时刻只有一个扫描者。开始扫描时：

```sql
UPDATE processing_batches
SET scan_owner = :worker
WHERE batch_no = :batch_no
  AND scan_status IN ('RUNNING', 'INTERRUPTED')
  AND scan_owner IS NULL;
```

影响行数必须为 1，否则本进程不得插入登记。不设租约超时秒数。进程崩溃后的续跑由调用方先确认原进程已经退出，再把该批次的 `scan_owner` 置空，然后重新执行上面的语句。两个同时来抢的调用方只有一个能把空主人改成自己。

候选路径先收齐，再按 Unicode 码点序排序。这个顺序与 PostgreSQL `COLLATE "C"` 的 UTF-8 字节序一致。每处理完一条才提交。成功登记或幂等命中时，同一事务里：

```sql
UPDATE processing_batches
SET cursor_path = :canon,
    files_registered = files_registered + 1
WHERE id = :batch_id
  AND scan_owner = :worker
  AND (cursor_path IS NULL OR cursor_path < :canon COLLATE "C");
```

永久拒绝且词法路径仍在源根内时，同一事务把 `cursor_path` 设为该路径，并把 `skipped_count` 加 1，不插入 `file_registry`。`lstat` 失败不推进游标。

中断后续跑使用同一个 `batch_no`，只处理严格大于 `cursor_path` 的候选。`cursor_path` 为空则从头处理。不得把已有批次的游标改回空值来“重头计数”。整批重跑是新建另一个 `batch_no`，从头扫描同样的源根。新批次命中已有路径时读回原 `file_id`，不修改 `file_registry.batch_id`，不新插入登记行。

重复消息：再执行一次上面的插入。冲突后读回原 `file_id`。若游标已经不小于该路径，游标和 `files_registered` 都不变。`seen` 里有没有这个 `task_id`，都不改变行数。

队列信封的键是 `task_id`。业务载荷至少包含 `file_id`，以及 `content_version`（尚未确认哈希时为 JSON `null`）。载荷里的 `file_id` 必须等于该 `task_id` 在 `processing_tasks` 中的 `file_id`。载荷不得携带另一枚新的 `file_id`。

### 历史数据

`file_id = task_id` 只适用于本规则落地前已经写在 `doc_tasks` 里的行。一次性复制可以把当时的 `doc_tasks.task_id` 抄进 `file_registry.file_id` 和对应的 `processing_tasks.task_id`。复制后的文本必须仍是 32 位小写十六进制，`id_origin='LEGACY'`，`task_origin='LEGACY'`。`created_at` 取 `doc_tasks.updated_at`；旧时间为空时才用复制事务的时间。

禁止把这些旧值改成带连字符的 UUIDv7，禁止为了统一格式回写 `doc_tasks.task_id`。新扫描禁止再把 `task_id` 写进 `file_id`。

同一 `TEXT` 列里的两种值：

| 来源 | 列中的原文 | 来源标记 |
|---|---|---|
| 已复制的旧 `doc_tasks.task_id` | 32 位小写十六进制，无连字符 | `LEGACY` |
| 新登记 | 36 位小写、带连字符的 UUIDv7 | `V7` |

相等比较用原文，不用 UUID 类型转换。旧行与 `doc_tasks.task_id` 的连接是字符串相等。数据库检查允许这两种形态，因此检查本身分不出“谁在插入”。扫描路径必须写 `V7`，并且新 `task_id` 不得等于 `file_id`。测试在扫描入口上断言，不靠一条无法区分写入者的检查来代替。

扫描响应同时给出 `file_id` 和 `task_id`。新建的 `V7` 行二者不得相等。读到的历史 `LEGACY` 行允许二者相等，且不得在响应前改写。当前 HTTP 实现仍只返回 `task_ids`，接口文档的改法见第 12 节。

### 各模块

| 模块 | 生成 | 使用 | 禁止 |
|---|---|---|---|
| Registry | 只生成新 `file_id` | 写入规范 `source_path` | 不生成 `task_id`；不把 `task_id` 写入 `file_id`；不写 Redis `seen`；不把路径哈希写入 `source_sha256` |
| Backend | 只在首次插入 `SCAN` 行时生成该行的 `task_id` | 扫描响应同时返回 `file_id` 与 `task_id` | 新 `V7` 响应中二者不得相等；不得用 `store.create_task` 的 UUIDv5 充当 `file_id` |
| Scheduler | 只在首次插入非 `SCAN` 阶段行时生成该行的 `task_id` | 队列键用 `task_id`；载荷带 `file_id` 与 `content_version` | 不生成 `file_id`；不得用 `seen` 判断这条路径有没有登记 |
| Parser | 不生成身份 | 按 `file_id` 计算 64 位小写字节哈希，经第 2b 节事务回写 | 不得自造 `file_id` |
| Classifier | 不生成身份 | 只读 `file_id` | 不得自造 `file_id` |
| Archive | 不生成身份 | 只读 `file_id`。临时名 `.part-{uuid4}` 只标记未完成文件 | 不得把临时 `uuid4` 或 SHA-256 前缀当作 `file_id` |

### 测试断言

下面每一条都应当能写成自动测试。相似度阈值不在这些断言里。

1. 新 `file_id` 匹配 UUIDv7 规范字符串，`id_origin='V7'`。它不等于 `str(uuid5(NAMESPACE_URL, "file:"+路径))`，也不等于 `uuid5(NAMESPACE_URL, 路径+":"+路径 SHA-256 前 32 位).hex`。
2. 同一进程内连续生成的新 ID，按字符串字典序严格递增。注入时钟回拨后，新 ID 的时间戳前缀不得小于上一枚。
3. `/data/pdfs/./a.pdf`、`/data/pdfs//a.pdf`、`/data/pdfs/sub/../a.pdf` 在源根 `/data/pdfs` 下得到同一个 `source_path` `/data/pdfs/a.pdf` 和同一个 `file_id`。
4. 源根 `/data/pdfs` 不接受 `/data/pdfs/../secret/a.pdf`，也不接受 `/data/pdfs2/a.pdf`，这两次都不插入行。
5. 相对路径不插入行。符号链接不插入行，链接目标也不会变成 `file_id`。
6. `/data/pdfs/A.pdf` 与 `/data/pdfs/a.pdf` 是两行、两枚 `file_id`。路径不被改成小写。
7. 含代理码位的路径不插入 `file_id`。
8. 两个事务并发插入同一规范路径：`file_registry` 只有一行，两边读到的 `file_id` 相同，落败的那枚 UUIDv7 不在表中。
9. 两个不同规范路径的字节 SHA-256 相同：两行、两枚 `file_id`，`source_sha256` 相等，插入都不失败。`dedup_records` 有两行 `kind='EXACT'`，`group_sha` 等于该哈希，且只有一个 `is_master`。本规则不写 `archive_type`，不插入 `NEAR`。
10. 只有一个文件拥有某哈希时，`dedup_records` 没有它的 `EXACT` 行。
11. 已有内容版本时，只改变 `mtime` 且新哈希与当前版本相同：`content_version` 不变，`mtime` 更新，任务的 `status` 与 `task_id` 不变。
12. `source_sha256` 仍为空时，磁盘上的 `mtime` 变了：不插入内容版本，`content_version` 保持空，`file_id` 不变，登记行上的 `mtime` 与 `bytes` 仍是首次 `lstat` 的值。
13. 首次算出哈希：插入 `content_version=1`，登记行的哈希与版本行相同，任务行数不变，`status` 与 `retry` 不变，`task_id` 不变。
14. 再次算出不同哈希：版本变成 `N+1`，旧版本行的哈希仍是旧值。`SCAN` 行的 `status` 不变。任一 `stage<>'SCAN'` 的行变为 `PENDING`、`retry=0`、错误列为空，`task_id` 不变。`archive_executions` 的行数与 `COMPLETED` 状态不变，目标 PDF 还在。
15. 同一路径的哈希按 A、B、A 变化：三个内容版本，哈希依次为 A、B、A，`file_id` 不变。
16. 三个合法文件，第一条提交后中断：续跑后登记仍是三行，`files_registered=3`，游标等于排序后的最后一条路径。
17. 对已提交路径再投递一次：仍是一行，游标不后退，`files_registered` 不增加。`seen` 为空或已含该 `task_id` 时，行数都是 1。
18. 历史复制行的 `file_id` 仍是原来的 32 位十六进制，重扫不把它改成 UUIDv7。新插入的 `V7` 任务若与 `file_id` 相等，检查失败。
19. 把 32 位路径哈希写入 `source_sha256` 失败。第二个相同字节哈希的路径可以插入。
20. 空文件的字节哈希是 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`。这只验证哈希对象是文件字节。

## 1 processing_batches（批次）

用途：给约 900 万份文件划分批次和断点。不保存单文件结论。

`id` SERIAL 主键。`batch_no` TEXT UNIQUE，且非空。`source_roots` TEXT NOT NULL，内容是 JSON 数组，至少有一个字符串。示例：`["/data/pdfs","/mnt/incoming"]`。每个元素都是已经按身份规则规范化的源根，区分大小写，不解析符号链接，不能是 `/`。检查：`jsonb_typeof(source_roots::jsonb) = 'array'` 且数组长度大于等于 1。`created_at`。

断点列：`cursor_path` TEXT NULL `COLLATE "C"`；`scan_status` TEXT NOT NULL，取值为 `RUNNING`、`INTERRUPTED`、`COMPLETED`、`FAILED`；`files_registered` INTEGER NOT NULL 默认 0；`skipped_count` INTEGER NOT NULL 默认 0；`scan_owner` TEXT NULL；`last_error` TEXT NULL。新建批次时 `scan_status='RUNNING'`，`cursor_path` 为空，`scan_owner` 为空。扫完最后一条候选后，把 `scan_status` 改为 `COMPLETED` 并清空 `scan_owner`。

子表里的 `batch_id` 指向本表 `id`，外键 `ON DELETE RESTRICT`。推进游标和抢占 `scan_owner` 的语句见身份规则。同一 `batch_no` 的续跑从严格大于 `cursor_path` 的候选继续。从头再扫必须新建 `batch_no`。

## 2 file_registry（登记）

用途：一份源 PDF 一行，保存登记身份和源位置。不保存分类结论。

`file_id` TEXT `COLLATE "C"` 主键。`source_path` TEXT `COLLATE "C"` NOT NULL。`source_sha256` CHAR(64) 可空。`bytes` BIGINT NOT NULL。`mtime` TIMESTAMPTZ NOT NULL。`batch_id` 外键指向第 1 表。`content_version` INTEGER NULL。`id_origin` TEXT NOT NULL。`created_at` TIMESTAMPTZ NOT NULL。

约束名：

- `uq_file_registry_source_path`：`UNIQUE (source_path)`。
- `ix_file_registry_source_sha256`：`source_sha256` 的普通索引，不是唯一索引。
- `ix_file_registry_batch_id`：`batch_id` 的普通索引。
- `fk_file_registry_batch`：`batch_id` 引用第 1 表，`ON DELETE RESTRICT`。
- `chk_file_registry_file_id_form`：`id_origin='LEGACY'` 时 `file_id` 匹配 `^[0-9a-f]{32}$`；`id_origin='V7'` 时 `file_id` 匹配 UUIDv7 规范字符串。
- `chk_file_registry_source_sha256`：`source_sha256 IS NULL OR source_sha256 ~ '^[0-9a-f]{64}$'`。
- `chk_file_registry_content_version`：`content_version IS NULL OR content_version >= 1`。

不得对 `source_sha256` 或 `(source_sha256, bytes)` 做唯一约束。精确重复的第二份文件，包括专利副本，必须能登记。重复关系放在第 4 表。

`file_id`、`source_path`、`id_origin`、`batch_id`、`created_at` 插入后不更新。`source_sha256`、`bytes`、`mtime`、`content_version` 只按第 2b 节更新。首次插入时哈希为空，`content_version` 为空，`bytes` 与 `mtime` 来自当时的 `lstat`。

## 2b file_content_versions（源字节版本）

用途：记录同一 `file_id` 已经确认过的字节版本。它不改变第 1 到第 10 表的编号。它也不是第 6、7、9 表的决策版本。本表只插入，不更新，不删除。

列：`file_id` TEXT NOT NULL；`content_version` INTEGER NOT NULL；`source_sha256` CHAR(64) NOT NULL；`bytes` BIGINT NOT NULL；`mtime` TIMESTAMPTZ NOT NULL；`batch_id` INTEGER NOT NULL；`observed_at` TIMESTAMPTZ NOT NULL。

主键 `pk_file_content_versions` 是 `(file_id, content_version)`。`fk_file_content_versions_file` 引用 `file_registry(file_id)`，`fk_file_content_versions_batch` 引用第 1 表，两者都是 `ON DELETE RESTRICT`。`chk_file_content_versions_ver` 要求 `content_version >= 1`。`chk_file_content_versions_sha` 要求 `source_sha256` 匹配 `^[0-9a-f]{64}$`。`ix_file_content_versions_sha` 是 `source_sha256` 的普通索引，不是唯一索引。同一文件可以在版本 1 与版本 3 用回同一个哈希，因此不对 `(file_id, source_sha256)` 做唯一约束。

何时插入版本 1：该 `file_id` 还没有任何内容版本，并且这次已经算出 64 位小写字节哈希。同一事务内插入版本 1，把登记行的 `source_sha256`、`bytes`、`mtime`、`content_version` 写成这次确认的值，再把该文件已有任务行的 `content_version` 设为 1。不改任务的 `status`、`retry`、`task_id`。首次确认前 `bytes` 与哈希长度不一致时，仍记版本 1，并以这次读到的字节数为准。

何时加 1：已经存在版本 `N`（`N>=1`），新算出的哈希与版本 `N` 的 `source_sha256` 不同。同一事务内插入 `N+1`，并用 `WHERE file_id=:id AND content_version=N` 更新登记行。更新行数不是 1 就回滚，由调用方重读最新版本后再决定。并发的两个不同哈希不会写出两个相同的 `content_version`。落败的一方若发现自己的哈希已经等于新的最新版本，就停止，不再加版本。

何时不加：

- 新哈希等于版本 `N` 的哈希：不插入。把登记行的 `mtime` 更新为这次观察到的时间。`bytes` 必须与该哈希对应的字节数相同；字节数不同则本次计算作废，登记行与版本行都不改，哈希任务记为 `FAILED`。
- 哈希还没算完，包括结果仍为空：不插入，也不因为 `mtime` 或 `bytes` 变了就加版本。内容版本尚未出现时，重复扫描也不改登记行上的 `bytes`、`mtime` 和 `source_sha256`，首次 `lstat` 的值保留到第一次哈希确认。已有版本 `N>=1` 时，`source_sha256`、`bytes`、`mtime`、`content_version` 都保持不变。
- 仅 `mtime` 变化而哈希相同：不加版本。

内容版本从 `N` 变为 `N+1` 时，同一事务还要重置处理任务，并按第 4 表调整 `EXACT` 组成员：

1. `stage='SCAN'` 的行只把 `content_version` 改为 `N+1`。`status`、`retry`、`task_id` 不动。
2. 其他阶段的已有行改为 `status='PENDING'`、`retry=0`、`error_code` 与 `error_msg` 为空、`content_version=N+1`。不删除行，不更换 `task_id`，不在本事务里插入新阶段。
3. 不插入 `archive_decisions`，不把已有 `COMPLETED` 改为 `SUPERSEDED`，不删除目标 PDF，也不删除源 PDF。以后若重新处理写出新的决策版本，仍按第 10 节在同一个归档事务里切换主归档。
4. 工作者提交阶段结果时，更新条件必须带上它开始时看到的 `content_version`。影响行数为 0 就丢弃这次结果，不写新的决策行。

版本 1 的事务同样维护第 4 表的 `EXACT` 组，但只把已有任务行的 `content_version` 设为 1，不执行上面第 2 步的打回 `PENDING`。

## 3 processing_tasks（执行态）

用途：记录某个文件在某个阶段的当前执行，不代替归档结果。

`task_id` TEXT `COLLATE "C"` 主键。`file_id` 外键指向第 2 表，`ON DELETE RESTRICT`。`stage` TEXT NOT NULL。本规则只冻结登记阶段的名字 `SCAN`；其他阶段沿用该行已经写入的 `stage`，升版重置不依赖一份新的阶段清单。`status` TEXT：`PENDING`、`RUNNING`、`DONE`、`REVIEW`、`FAILED`。`retry` INT NOT NULL 默认 0。`error_code`，`error_msg`，`updated_at`。`content_version` INTEGER NULL。`task_origin` TEXT NOT NULL，取值为 `LEGACY` 或 `V7`。

约束名：

- `uq_processing_tasks_file_stage`：`UNIQUE (file_id, stage)`。同一文件同一阶段只有一行。失败重试把这一行的 `retry` 加 1，不新插入一行。内容升版按第 2b 节把非 `SCAN` 行打回 `PENDING` 并把 `retry` 置 0，仍然不新插入。
- `fk_processing_tasks_content`：`(file_id, content_version)` 引用第 2b 表，`ON DELETE RESTRICT`。`content_version` 为空时，按 PostgreSQL `MATCH SIMPLE` 不检查这对外键。
- `chk_processing_tasks_task_form`：`task_origin='LEGACY'` 时 `task_id` 为 32 位小写十六进制；`task_origin='V7'` 时 `task_id` 为 UUIDv7 规范字符串。
- `chk_processing_tasks_new_task_ne_file`：`task_origin<>'V7' OR task_id<>file_id`。新行不得与 `file_id` 同值；历史 `LEGACY` 行允许同值。
- `INDEX(status)` 供未完成任务回扫。该索引尚未在真实库压测。`UNIQUE(file_id, stage)` 的左前缀用于按 `file_id` 查找，不另建一条单独的 `file_id` 索引。

新 `task_id` 在该 `(file_id, stage)` 第一次插入时生成，之后不更新。`SCAN` 由 Backend 生成，其他阶段由 Scheduler 生成。Registry 不生成 `task_id`。

## 4 dedup_records（去重）

用途：记录重复组成员。每个成员一行，因此同一 `group_sha` 可以对应多份文件，包括必须保留的专利副本。本表不决定主目录，也不删除源文件或已有归档副本。

`id` SERIAL 主键。`group_sha` CHAR(64) NOT NULL。`file_id` 外键指向第 2 表。`is_master` BOOLEAN NOT NULL。`master_id` 外键指向第 2 表。`kind` TEXT NOT NULL。`created_at`。

约束名：

- `uq_dedup_records_file_kind`：`UNIQUE (file_id, kind)`。
- `ix_dedup_records_group_sha`：`group_sha` 的普通索引，不是唯一索引。
- `uq_dedup_one_master`：部分唯一索引 `UNIQUE (group_sha, kind) WHERE is_master`。
- `chk_dedup_records_sha`：`group_sha` 匹配 `^[0-9a-f]{64}$`。
- `chk_dedup_records_kind`：当前只允许 `EXACT`。需求第 10 节第 4 项的近重复阈值仍 TBD，本文不写相似度，也禁止插入 `NEAR`。阈值批准后再放宽这个检查。
- `chk_dedup_records_exact_master`：`EXACT` 行的 `master_id` 非空。
- 两条 `file_id` 外键都是 `ON DELETE RESTRICT`。

组的维护放在第 2b 节那个确认哈希的事务里，不另做一套异步口径。

至少两个登记行的 `source_sha256` 同为某一个 64 位小写哈希，并且都已经有内容版本时，这些文件各有一行 `EXACT`。`group_sha` 等于该哈希。只有一个文件拥有该哈希时，不写 `EXACT` 行。

主件是这些成员里 `file_registry.created_at` 最早的 `file_id`。时间相同则取 `file_id` 按 `COLLATE "C"` 升序的第一个。该行 `is_master` 为真，其余为假。每一行的 `master_id` 都等于主件的 `file_id`。后加入的文件 `created_at` 更晚，不抢走已有主件。删除成员后若原组仍有两行或更多，按同一规则重算；若只剩一行，把这最后一行也删掉。`id` 可以因删除重插而变化，`file_id` 不变。

不同路径、相同字节哈希：各自保留自己的 `file_id`，本组只说明它们同组。专利副本也这样登记。禁止因哈希相同拒绝第二份登记。

## 5 parse_artifacts（解析证据引用）

用途：保存解析类型和有限文本证据的引用。不保存整份 PDF。

`id` SERIAL 主键。`file_id` 外键。`pdf_type` TEXT，`evidence_mode` TEXT，`query_text` TEXT（不超过 3000 字），`title` TEXT，`ocr_mean` FLOAT 可空，`parse_ref` TEXT 可空（大对象的外部位置），`created_at`。`INDEX(file_id)`。OCR 原文和页图不进本表正文，避免 900 万行把数据库撑成文件库。

## 6 exclusion_decisions（排除判定）

用途：保存专利门和低价值门的机器或人工证据。确认专利或确认低价值时，可以没有第 7 表的业务分类行。

`id` SERIAL 主键。`file_id` 外键。`version` INT，与第 9 表同一轮版本对齐。`patent_hit` BOOL 可空，空表示尚未能判断，不得默认成否。`patent_ev` JSONB。`low_value` JSONB，可记录 LV01～LV05 的多个命中和证据。`decided_by` TEXT：`RULE`、`BGE`、`LLM`、`HUMAN`。`created_at`。`UNIQUE(file_id, version)`。

多个低价值原因同时命中时，主目录优先级 TBD。未批准前不写第 9 表的正式低价值目录，决策进入 `PENDING`。

## 7 classification_results（4/27）

用途：保存业务分类尝试和机器判定。专利、低价值、待复核不必有本表行。

在旧表上扩展：`id` 主键，`file_id` 外键，`version` INT，`level1`、`level2` TEXT（必须能在 taxonomy-v3 中找到合法父子，否则不得归档），`scores` JSONB，`source` TEXT，`taxonomy_version` TEXT，`basis` JSONB。`UNIQUE(file_id, version)`，`INDEX(level2)`。旧列 `result_type`、`task_id`、`level1`、`level2` 保留。复核不得 UPDATE 覆盖机器写下的 `level1`、`level2` 和 `basis`；人工修改写入第 8 表。

旧 `result_type` 的读法：`CLASSIFIED` 表示当时判过业务类，不等于已经可以写入 27 个目录。`IRRELEVANT` 只在兼容视图里显示为“历史无关，待确认”，禁止迁移脚本把它批量改成已批准的 LV04。`MANUAL_REVIEW` 与 `UNRESOLVED` 都表示待复核，不产生业务目录。

## 8 review_records（复核）

用途：追加人工复核历史。不回写第 7 表的机器判定列。

`id` SERIAL 主键。`file_id` 外键。`from_version` INT，`to_version` INT。`reviewer` TEXT NOT NULL。`from_target` TEXT，`to_target` TEXT，`note` TEXT，`created_at`。`status` TEXT：`OPEN`、`RESOLVED`。关闭时 `to_version = from_version + 1`，并产生第 9 表的新版本。已有代码把 `reviewed_by` 写在结果行上，那是旧行为；新写入以本表为准。

## 9 archive_decisions（归档决策）

用途：某一版唯一主目录。一个 `file_id` 加一个 `version` 只有一条。Worker 只消费本表，不消费模型现场拼出的路径。

`id` SERIAL 主键。`file_id` 外键。`version` INT。`archive_type` TEXT：`PATENT`、`LOW_VALUE`、`BUSINESS`、`PENDING`。`decision_status` TEXT：`APPROVED` 或 `NEED_REVIEW`。`level1`、`level2` 仅 `BUSINESS` 使用，且必须符合 taxonomy-v3 父子关系。`reason` TEXT，低价值时为 `LV01`～`LV05`；主原因未批准且命中多个原因时留空，并把 `archive_type` 设为 `PENDING`。`target_dir` TEXT，只能来自映射表。`target_file` TEXT 可空，文件名算法 TBD，空着也不许由模型填自由路径。`approved` BOOL：为真只表示允许 Worker 按本版复制，包含待复核暂存；不表示业务正式归档已经完成。`UNIQUE(file_id, version)`。

`PENDING` 对应目录 `04_待复核暂存/`，决策状态为 `NEED_REVIEW`。业务要求的暂存事实用 `archive_type=PENDING` 表示，不再单列一个会和 `archive_type` 冲突的 `staging_status`。若业务方要求独立列名，记为 TBD。

## 10 archive_executions（执行校验）

用途：某一版决策的一次复制和校验。决策可以有多条历史执行，但一个文件只能有一条 `COMPLETED` 主记录。

`id` SERIAL 主键。`decision_id` 外键指向第 9 表。`file_id` TEXT NOT NULL，必须与该决策的 `file_id` 相同，写入事务里检查。`tmp_path` TEXT，`final_path` TEXT 可空。`bytes_ok`、`sha_ok`、`src_unchanged` 在设计语义上是布尔；`backend/models.py` 和 `002` 草案目前用整数 0/1。迁移未验证前不要混用两种比较写法。`status` TEXT：`QUEUED`、`COPYING`、`VERIFYING`、`COMPLETED`、`FAILED`、`SUPERSEDED`。`completed_at` 可空。`INDEX(status)`。

`COMPLETED` 必须同时满足：目标文件路径已写入、`bytes_ok`、`sha_ok`、`src_unchanged` 都为真。约束形式：

```sql
CHECK (status <> 'COMPLETED' OR (bytes_ok AND sha_ok AND src_unchanged AND final_path IS NOT NULL))
```

整数列在真实 PostgreSQL 上应写成 `= 1`，与 `002` 草案一致。该语句还没有在真实 PostgreSQL 执行过。

一个文件只有一个有效主归档：

```sql
CREATE UNIQUE INDEX one_active_archive ON archive_executions (file_id) WHERE status = 'COMPLETED';
```

复核改类时，先在同一事务里把旧的 `COMPLETED` 改为 `SUPERSEDED`，再把新行更新为 `COMPLETED`。不能先插入第二条 `COMPLETED`。`final_path` 不做全表唯一：废弃行会留下旧路径。只对仍有效的完成行限制路径：

```sql
CREATE UNIQUE INDEX one_final_completed ON archive_executions (final_path) WHERE status = 'COMPLETED' AND final_path IS NOT NULL;
```

正式归档完成的统计条件是：`status = COMPLETED`，三项校验为真，且对应决策的 `archive_type` 属于 `PATENT`、`LOW_VALUE`、`BUSINESS`。`archive_type = PENDING` 的完成行是暂存，不计入业务正式归档。

## 11 规模、兼容与 002 的验证状态

900 万份文件时，第 2 表约 900 万行，用 `file_id` 主键、`source_path` 唯一和 `source_sha256` 普通索引查找。第 2b 表在哈希确认后通常每文件一行，只有确认到字节哈希变化才追加，不把第 2 表拆成每文件多行。第 3、10 表按 `status` 回扫未完成工作。第 5 表只留有限 `query_text` 和外部引用。本文没有分区方案，也没有真实 PostgreSQL 上的千万级压测，不能宣称写入、校验或查询已经满足 2026-12-31 的吞吐。
