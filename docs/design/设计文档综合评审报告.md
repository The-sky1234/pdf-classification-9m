## 4. 接口与数据库一致性

一致的部分：

- 归档类型都是 `PATENT`、`LOW_VALUE`、`BUSINESS`、`PENDING`。
- `COMPLETED` 都要求目标路径、字节数、SHA-256、源未变化，并且数据库事务已提交。
- `PENDING` 的完成行不算业务正式归档。
- 决策版本以 `archive_decisions.version` 为准；复核追加历史，不覆盖机器判定。
- 专利和低价值可以没有 `classification_results` 业务行。
- H9 的返回字段能从第 9、10 表读出，不依赖尚未存在的 `staging_status` 列。

仍然要分开看的部分：

- 已有 HTTP 读写的是 `doc_tasks` 和 `classification_results`。10 张目标表里，ORM 只声明了归档决策和执行的一部分列，其余是计划。
- H5 继续接受旧五态，是为了保住冻结的门禁；归档决策不使用 `IRRELEVANT` 这个终态。
- H6、H7 的已有行为只处理 `MANUAL_REVIEW`。`UNRESOLVED` 进入同一复核队列是计划。
- `checksum_verified` 只是接口上的派生布尔值，库里以三项校验列为准。

## 7. 建议优先处理

1. 冻结 `file_id` 的唯一生成输入，并规定旧 `task_id` 只在迁移视图中等价。
2. 在真实 PostgreSQL 上验证 `002` 的检查约束和部分唯一索引，验证前不报完成。
3. 批准或明确推迟两个新场景的二级 ID。
4. 改 Redis 入队：同一业务键失败后可以重投，已 `COMPLETED` 的版本不得再复制。
5. 让 `GET /taxonomy` 改为读取 `taxonomy-v3.yaml`，避免继续把 25 类当成线上分类。
6. 用小样本把「分类决策 → 真实复制 → 三项校验 → `COMPLETED`」跑通，再谈 900 万规模。
