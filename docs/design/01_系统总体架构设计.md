## 1 分层与处理顺序

单机进程内分层：FastAPI 收单和查改；Parser 做类型检测与按需证据；Classifier 做漏斗判决；Scheduler 排队、断点和恢复；Archive Worker 复制并校验；PostgreSQL 记账存证；Redis 只传任务引用。

主流程与需求第 0 节、第 2 节同一顺序。精确去重已在上游完成，不再插在登记和解析之间：

Registry 按主件清单登记 `file_id` → Parser 先按格式做有效性检查和必要文本证据 → Features（query 不超过 3000 字）→ PatentGate → 低价值中不依赖相关性的三类（LV01、LV03、LV05；证据不足不得硬判）→ RelevanceGate → 只有确认属于业务范围才进入 Classifier（4 个一级、27 个二级）→ 低置信或冲突进入 Review → 已形成归档决定后交给 Archive。Scheduler 负责任务租约、重试和恢复。Backend 只读写台账，不判类，不拼路径。

LV02 不再收纳已经剔除的字节级副本。近重复判据未批准，本阶段不得自动归入 LV02。

顺序铁律：已确认专利 > 已确认低价值五类 > 已确认的 4/27 > 证据不足则 `PENDING`。三级线索只作证据。阈值和词表未批准时进入待复核。

RelevanceGate 的生产阈值尚未校准。禁止把 0.7、0.3 或任何未经验证的分数写成自动通过线。原始相似度不是分类正确概率。未校准结果不得标成 `APPROVED`。

确认无业务匹配只产生 LV04，归档类型为 `LOW_VALUE`，原因码 `LV04`，目录 `02_低价值文件/无业务匹配/`。新写入不得再把 `IRRELEVANT` 当成业务终态；旧数据只按 LV04 读兼容。

## 2 单卡运行方案

硬件写死：一台 Linux 服务器，1 张 NVIDIA RTX A6000，48GB，设备号 0。没有第二张卡。PostgreSQL、Redis、API、文本提取和归档复制都走 CPU。GPU 只在下面三个波次里使用，而且同一时间只启动一个波次。

只靠文件锁让 OCR、MinerU 和分类同时把权重留在显存里，48GB 不够，也跑不完约 700 万主件。所以改成先用 CPU 处理能抽出文字的文件，GPU 只处理剩下的那一截，并且每个波次只加载本波次的模型。`gpu-a6000.lock` 只作为误把两个波次同时拉起来时的保险。

```mermaid
flowchart LR
    A[主件清单] --> B[波次0 CPU: 抽文字和规则]
    B --> C{还缺什么}
    C -->|有文字| E[波次2: BGE 与 Reranker]
    C -->|扫描页或图片| D[波次1: 只开 PaddleOCR]
    D --> E
    C -->|抽不出且不是扫描件| R[待复核]
    E --> F{分差够且已校准?}
    F -->|是| G[写入结论并 CPU 复制归档]
    F -->|否| H{大模型放得进剩余显存?}
    H -->|是| I[有限次调用]
    H -->|否| R
    I --> G
    I --> R
```

### 2.1 波次

| 波次 | 谁在跑 | 显卡上有什么 | 处理哪些文件 |
|---|---|---|---|
| 0，常开 | `parser-worker` 可按 CPU 核数横向扩展；归档复制也在 CPU | 不占 GPU | 全部主件。抽文字、做有效性检查、用文件名和已抽出的文字做专利与低价值规则 |
| 1，按需 | 只启动 `ocr-worker`。先停掉分类和 MinerU | 只加载 PaddleOCR | 没有可用文字层的 PDF 扫描页，以及 jpg、png、tif 等图片。有文字的文件不进这一波 |
| 2，按需 | 只启动 `classify-worker`。先停掉 OCR 和 MinerU | 只加载 bge-m3 和 bge-reranker-v2-m3 | 已经有短证据、且规则没有定论的文件。先判是否属于 27 个场景，再选一级和二级 |
| MinerU，默认不跑 | 只启动 `mineru-worker`。先停掉另外两个 GPU 容器 | 只加载 MinerU | 不进入主路径。波次 1 仍读不出可用文字的复杂 PDF，默认待复核。只有单独批准一批样本后，才停掉其他波次，专门跑这一批 |

显存配额是设计上限，用来决定能不能加载，不是实测峰值。上卡后若超过配额，这个模型退出当前波次，对应文件改走待复核：

- 整卡 48GB，始终留出不少于 8GB，不分配给权重。
- 波次 1：PaddleOCR 不超过 24GB。
- 波次 2：bge-m3 与 bge-reranker-v2-m3 合计不超过 16GB。
- 大模型不常驻。只有选定的权重加运行时不超过 20GB，并且与这两个向量模型加在一起仍低于 40GB 时，才允许在波次 2 里启动。放不下就关掉大模型，分差不够的文件直接待复核。
- MinerU 单独运行时不超过 40GB。

旧架构里按 4 张 GPU 估算的页速度作废。在这张 A6000 上用真实主件做 Benchmark 之前，不写吞吐承诺，也不承诺 2026-12-31 一定跑完。

### 2.2 波次 0 怎么取文字

| 格式 | 做法 |
|---|---|
| 有文字层的 PDF | PyMuPDF，CPU |
| docx、xlsx、pptx | CPU 读取 OOXML 正文，不转成 PDF，不进 GPU |
| 旧版 doc、WPS、OFD | 本阶段没有批准的提取器。抽不出文字就待复核，不送进 MinerU |
| jpg、png、tif 等图片，以及没有文字层的 PDF | 交给波次 1 |
| zip、rar、dwg、音视频、数据库 | 只登记，不打开、不解包，待复核 |

压缩包一旦解开就会改变「700 万主件」这个边界，所以不自动解。

### 2.3 判断仍然不靠把每份文件送进大模型

专利、无效文件、内容不足、否定词在波次 0 用规则。词表和阈值没批准的，待复核。

bge-m3 负责「是否属于这 27 个场景」和一级召回。bge-reranker-v2-m3 只在已经选定的那个一级里面重排二级。自动通过仍然要等阈值校准；没校准就待复核。大模型只在波次 2、显存放得下、而且分差不够时调用有限次数，只能在给定候选里选，也可以回答不确定。

### 2.4 部署约束

- 源目录只读。`ARCHIVE_ROOT` 在扫描源之外。
- 默认 `docker compose up` 只起数据库、Redis、API 和 CPU 的 `parser-worker`。三个 GPU 容器分别挂在 profile `ocr-wave`、`classify-wave`、`mineru-wave` 上，不会一起起来。
- 切换波次用 `deploy/ops.sh` 的 `wave-ocr`、`wave-classify`、`wave-mineru`。每个命令会先停掉另外两个 GPU 容器。
- Redis 键名仍是 `pdf_tasks`。消息只带 `file_id`、`task_id`、`content_version`，不带正文。这个键名不表示只处理 PDF。

## 3 模块职责

| 模块 | 职责 | 明确不做 |
|---|---|---|
| Registry | 登记上游主件清单中的路径；新 `file_id` 为 UUIDv7，只在首次插入成功时留下。清单里的扩展名写入台账 | 不分类，不复制归档；不把清单外的精确重复副本登记进来；不用 `seen`、路径哈希或 uuid5 做登记幂等 |
| Dedup | 本阶段不运行。精确去重是上游已完成事实。近重复只在判据批准后才允许产出证据 | 不重扫约 980 万份；不删除源；不把已剔除副本送入 LV02 |
| Parser | 波次 0 在 CPU 上按第 2.2 节取文字。只有扫描页和图片进入波次 1 的 PaddleOCR | 不判决类别；不把非 PDF 批量转成 PDF；MinerU 不在主路径 |
| Features | 清洗后的有限 query 和页码证据 | 不落归档路径 |
| PatentGate | 用文件名、元数据、首页、专利号等多证据确认专利 | 不得因缺文本判成非专利 |
| LowValueGate | 判断 LV01、LV02、LV03、LV05 | 词表和阈值未批准时不自动排除；LV04 不在本门硬判 |
| RelevanceGate | 输出相关、确认无匹配或不确定 | 低分不等于无匹配；确认无匹配才映射为 LV04 |
| Classifier | 只对相关文件做 4/27，并校验父子关系；疑难件有限次 LLM | 不拼目录；综合管理不是兜底类 |
| Review | 人工确认或改判，决策版本加 1，保留机器原判断 | 不覆盖历史记录 |
| Archive | 按 taxonomy-v3 映射复制、校验、回写 | 不移动、不删除源；不接受调用方自造路径 |
| Scheduler | Redis 队列、优先级、租约、断点和重投 | `seen` 不是登记幂等，不得用它判断路径是否已登记。它只挡住同一队列消息重复入队，不永久拒绝失败后的合法重试。登记幂等在 PostgreSQL |
| Backend | HTTP、事务、台账查询和复核写入 | 不做算法，不执行文件复制 |

## 4 数据流、存储与归档恢复

PostgreSQL 是权威状态，保存文件、任务、源字节版本、决策版本、复核、归档执行和审计。新 `file_id` 与新 `task_id` 都是 RFC 9562 UUIDv7（36 位小写、带连字符，列类型 TEXT），新行二者不得相等。已经复制的历史行保持 32 位小写十六进制，允许二者相等，不得改写成 UUIDv7。`batch_id` 是批次表的整数代理键，不得当作 `file_id`。登记幂等在 PostgreSQL，靠规范路径唯一约束 `uq_file_registry_source_path`。同一路径内容变化时 `file_id` 不变，只追加 `content_version`。不同路径即使字节哈希相同也分别登记。`source_sha256` 只保存文件字节哈希，可空且非唯一；路径字符串哈希不得写入该列。

Redis 仍只传小消息。`pdf_tasks` 的信封键是 `task_id`，载荷带 `file_id`、`task_id` 与 `content_version`（哈希未确认时为 JSON `null`）。`archive_tasks` 携带 `file_id`、决策 `version`，以及该决策所依据的 `content_version`。决策 `version` 是判决版本，与 `content_version` 不是同一个数。Worker 见到严格更旧的 `content_version` 就丢弃，不写决策、不复制。消息与当前版本都为空时不是更旧，仍可处理。PDF 正文和解析全文不进 Redis。队列丢失时，按 PostgreSQL 里未完成的状态重新入队，不插入第二个 `file_id`。`seen` 只描述当前队列实现里的投递记录，不是文件登记幂等。

成本顺序：能直接抽出文字就直接提取；只对扫描页、图片型页面和图片补必要 OCR；LLM 只用于疑难件，并且有次数上限，到达上限后进入待复核。阶段一不做全量 Markdown、全量全文 OCR 和全量 LLM。

登记入口：上游去重只做了标记，不删除、不移动源文件，因此扫描根里仍可能同时有主件和副本。目标设计以主件路径清单作为登记输入。副本不建 `file_id`，不进处理队列。只有在扫描根里已经不存在这些副本时，全目录扫描才和主件清单等价。已有 `POST /tasks/scan` 只收集 `.pdf`，这是当前代码，不是目标行为。

归档文件名保留源扩展名。目标相对目录仍只查 taxonomy-v3，不因格式多出一层目录。

归档闭环以 `contracts/phase1/archive-contract.md` 为准，要点如下：

1. 已批准决策写入正式目录。决策为 `NEED_REVIEW` 时，实体进入 `04_待复核暂存/`，使用独立暂存状态，不计入业务正式归档。
2. 目标相对目录只查 `contracts/phase1/taxonomy-v3.yaml`：`PATENT` → `01_专利文件/`；`LOW_VALUE` → `02_低价值文件/{五类目录名}/`；`BUSINESS` → `03_业务分类/{一级目录}/{二级目录}/`；`PENDING` → `04_待复核暂存/`。非法一级、二级组合拒绝写入。
3. 在目标文件系统写临时文件，流式复制，字节数和 SHA-256 都通过，且源指纹未变，再做原子替换。
4. 然后在 PostgreSQL 事务中写入 `archive_status=COMPLETED` 和目标路径。校验失败不得写 `COMPLETED`。源文件当前 `content_version` 大于该决策所依据的 `content_version` 时，也不得写 `COMPLETED`，不得用这份旧决策覆盖新内容。
5. 幂等：最终文件已在且校验通过，则补记 `COMPLETED`，不生成第二份副本；只剩下临时文件则删除后重来；库未提交则重新入队。
6. 复核改类时决策版本加 1。新副本校验成功后，旧执行标 `SUPERSEDED`。同一文件只保留一个有效主归档，不删除源 PDF。源字节 `content_version` 从 N 升到 N+1 时，不把已有 `COMPLETED` 改成 `SUPERSEDED`，不删除旧归档。旧决策保留，等新内容走完门控后再产生新的决策版本。
7. 可重试的 I/O 做有界重试。校验失败时删除临时文件后再重试。磁盘满则停批并告警。唯一文件名算法、是否允许硬链接仍为 TBD，现有代码里的命名函数不是已批准规则。
