# 05 接口详细设计（V3，可编码）

审查修订：2026-10-10。对照 `backend/app.py`、`backend/store.py`、`backend/schemas.py`、`scheduler/queue.py`、`scheduler/archive_worker.py` 和 `contracts/phase1/`。只改本文件。

标记：**已有**表示当前代码会这样做；**计划**表示契约或业务已经要求、但代码还没有。不要把计划写成已实现。模块、接口和流程图的可读设计见 `docs/阶段一_系统总体架构模块与接口详细设计_V3.md`。正式路由就是本文下面 9 个路径，不使用 `/api/v1/*`。

正式路由以 `contracts/phase1/api-contract.yaml` 的 9 个路径为准。除 `GET /archive/{file_id}` 外，其余 8 个已有实现。该 yaml 的 `POST /tasks/scan` 仍只写「沿用，返回 202」，没有下文计划响应里的 `file_id` 与 `items`。身份与扫描响应以本文件和 `docs/design/04_数据库详细设计.md` 为准。全部路由使用请求头 `X-Api-Key`。不匹配时 **已有** 返回 401，体为 `{"detail":"unauthorized: bad api key"}`。没有角色权限；更细的权限 TBD。

身份关系（编码时必须遵守）。生成规则以 `docs/design/04_数据库详细设计.md`「文件身份规则（已冻结）」为准，并与 `contracts/phase1/data-contract.md` 一致：

- `file_id` 标识一份源文件，绑定规范路径，不绑定字节内容。一个规范路径只有一个 `file_id`。
- `task_id` 标识该 `file_id` 在某个 `stage` 上的当前执行行。同一文件同一阶段只有一行。失败重试和内容升版不换 `task_id`。
- **已有** `POST /tasks/scan` 的 `task_id` = `uuid5(NAMESPACE_URL, 路径 + ":" + SHA-256(路径字符串)[:32]).hex`，32 位小写十六进制。这里的 `file_hash` 是路径字符串 SHA-256 的前 32 位，不是文件字节的 SHA-256，不能用于精确去重。
- **已有** `backend/registry.py` 的 `file_id` = `str(uuid5(NAMESPACE_URL, "file:" + 路径))`，36 位带连字符。它没有被扫描接口调用。上面两套 uuid5 只描述当前代码。
- **计划**：新 `file_id` 与新 `task_id` 都是 RFC 9562 UUIDv7，36 位小写、带连字符，列类型 TEXT。生成输入不含路径、不含哈希、不含 `NAMESPACE_URL`。新行 `id_origin=V7`、`task_origin=V7`，且二者不得相等。历史复制行 `id_origin=LEGACY`、`task_origin=LEGACY`，保持 32 位小写十六进制；允许 `file_id=task_id`，响应前不得改写。历史映射以数据库设计「历史数据」和第 11 节为准。
- `batch_id` 是 `processing_batches.id`（SERIAL）。不得当作 `file_id`。`file_registry.batch_id` 只记首次登记批次。
- `content_version` 是源字节版本。第 6、7、9 表的 `version` 是决策版本。二者不是同一个数。

## A. 九个 HTTP 接口

### H1 POST /tasks/scan【已有】

扫描只读源目录，为扫到的 PDF 建立任务。调用方是运维。不分类，不复制文件。

| 参数 | 位置 | 类型 | 必填 | 校验 |
|---|---|---|---|---|
| X-Api-Key | Header | string | 是 | 与服务端 `API_KEY` 一致，否则 401 |
| root | Body | string | 是 | 非空；**已有**要求是存在的目录，否则 400，`detail` 为 `root is not a directory` |
| limit | Body | int | 否 | **已有**默认 1000，范围 1～100000；超出由 Pydantic 拒绝 |
| batch_id | Body | int | 计划 | **已有**没有此字段。计划：传入已有批次的 `batch_id` 则按该行 `batch_no` 续跑；不传则新建批次并在响应里返回新的 `batch_id`。`batch_no` 只按 04 要求为非空且唯一的 TEXT，本文件不另定生成算法，也不得把 `batch_no` 或 `batch_id` 当作 `file_id` |

请求示例：

```json
{"root": "/data/pdfs", "limit": 1000}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| accepted | int | 本次返回的任务数，含已经存在的任务 |
| task_ids | string[] | **已有**对应 `doc_tasks.task_id`。计划与 `items` 同序，元素改为 `processing_tasks.task_id`，不删除此字段 |
| batch_id | int | **计划**。`processing_batches.id`，不得是 `file_id` |
| items | array | **计划**。元素含 `file_id`、`task_id`、`source_path`、`id_origin`、`content_version` |

成功响应示例（202，**已有**形状）：

```json
{"accepted": 2, "task_ids": ["<uuid5-hex>", "<uuid5-hex>"]}
```

**计划**在保留 `accepted` 与 `task_ids` 的同时增加字段。旧客户端仍只读这两个字段。`task_ids` 与 `items` 同序，`task_ids[i]` 等于 `items[i].task_id`。`batch_id` 是本次扫描所属批次的整数代理键，等于 `processing_batches.id`，不得填成 `file_id` 或 `batch_no`。整批重跑按数据库设计新建 `batch_no`，响应里的 `batch_id` 取该新行的 `id`。

```json
{
  "accepted": 2,
  "batch_id": 17,
  "task_ids": ["<v7-task-id>", "<v7-task-id>"],
  "items": [
    {
      "file_id": "<v7-file-id>",
      "task_id": "<v7-task-id>",
      "source_path": "/data/pdfs/a.pdf",
      "id_origin": "V7",
      "content_version": null
    }
  ]
}
```

新建 `V7` 行的 `file_id` 与 `task_id` 不得相等。读到的 `LEGACY` 行允许二者相等，且都是 32 位小写十六进制，`id_origin` 为 `LEGACY`，响应前不得改写。尚未确认字节哈希时 `content_version` 为 JSON `null`。

**已有逻辑**：`os.walk` 收集 `.pdf`，达到 `limit` 即停。每个路径调用 `store.create_task`。已有相同 `task_id` 则返回原行，不新插入。每个文件单独 `commit`。不写 `file_registry`，不调用 `registry.scan`，不计算文件字节哈希。

**计划**：本接口是扫描登记，不是单独的创建批次接口。不把 `/api/v1/batches` 写成正式接口。一次扫描建立或续跑一个 `processing_batches` 行。登记插入冲突于 `uq_file_registry_source_path` 时读回原 `file_id`；已有 `SCAN` 行则读回原 `task_id`，不改 `status`、`retry`、`task_id` 和 `file_registry.batch_id`。没有 `SCAN` 行时才插入，新 `task_id` 为另一枚 UUIDv7。登记事务不读、不写 Redis `seen`，不用路径哈希，不用 uuid5。投递时信封键为该 `task_id`，载荷带 `file_id` 与 `content_version`。`status=PENDING` 可以再次投递；不得为了入队再生成第二个 `file_id`。`root` 落在 `ARCHIVE_ROOT` 之内时返回 400，避免扫到归档副本。该校验当前没有。

同一 `batch_no` 的断点续扫使用 `cursor_path`（`COLLATE "C"`），只处理严格大于游标的候选。游标为空则从头。不得把已有批次的游标改回空值。已由冻结规则推出的扫描策略：路径字典序小于游标的新文件，本次续扫会漏掉。已扫过路径的内容变化，游标续扫不会再次打开它。续扫只保证不重复登记已处理路径。要发现游标之前的新路径或已登记路径的内容变化，必须另起一次全量或增量重扫（新 `batch_no`，仍走唯一约束，不产生第二个 `file_id`）。

**数据库**：已有只写 `doc_tasks`（`task_id`、`file_path`、`file_hash`、`stage=SCAN`、`status=PENDING`）。计划按数据库设计写 `processing_batches`、`file_registry` 和 `processing_tasks`。不同规范路径即使字节 SHA-256 相同也各插入一行。旧 `file_hash` 禁止写入 `source_sha256`。

**Redis**：已有不投递。`scheduler/queue.py` 的 `RedisQueue.enqueue` 存在，但扫描接口没有调用它。`seen` 不是登记幂等。

**状态与事务**：已有新任务 `PENDING`。事务边界是每个文件一次提交。没有跨文件事务。

**错误**：400 目录非法；401 密钥错误；422 由 FastAPI 在 `limit` 越界时返回。没有 413。

**幂等与测试**：已有：同一路径重复扫描返回原来的 `task_id`，不插第二行。`accepted` 仍等于本次扫到的文件数，不会变成 0。测试：合法目录 202；`root` 不是目录 400；无密钥 401；重扫主键不变。计划：同一路径重复扫描返回原来的 `file_id` 和原来的 `task_id`。

| task_id | Path | string | 是 | **已有**按主键查找；不存在 404，`detail` 为 `task not found` |

| 字段 | 类型 | 说明 |

成功响应示例（200）：


### H5 POST /results【已有】

保存一条分类结果。**已有**接口不复制 PDF，也不写归档决策。

| 参数 | 位置 | 类型 | 必填 | 校验 |
|---|---|---|---|---|
| result_type | Body | string | 是 | **已有**只允许 `CLASSIFIED`、`IRRELEVANT`、`MANUAL_REVIEW`、`FAILED`、`UNRESOLVED`，否则 400 |
| file_path | Body | string | 是 | **已有**模型列非空；缺失时数据库报错，不是稳定的 400 |
| level1 | Body | string | 条件 | `CLASSIFIED` 时必填；其他五态里的非 `CLASSIFIED` 只要带了 `level1` 或 `level2` 就 400 |
| level2 | Body | string | 条件 | 同 `level1` |
| task_id | Body | string | 否 | **已有**若能找到 `doc_tasks`，则把该任务改为 `stage=SAVE` |
| 其余证据字段 | Body | string/object | 否 | `relevance_status,evidence_mode,candidate_scores,decision_source,classification_basis,model_version,taxonomy_version,prompt_version,retry_count,error,file_hash` |

请求示例（已有门禁能接受的分类结果）：

```json
{"task_id": "abc", "file_path": "/data/a.pdf", "result_type": "CLASSIFIED", "level1": "L1_AQSC", "level2": "消防监管", "taxonomy_version": "v3.0-phase1"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 新插入的 `classification_results.id` |

成功响应示例（201）：`{"id": 1}`

**已有逻辑**：校验五态和“非 CLASSIFIED 不得带类别”。插入一行并 `commit`。若有 `task_id`，再更新任务并第二次 `commit`。不校验一级、二级是否属于 27 场景。不写 `archive_decisions`。

**计划**（不改变已有五态门禁，归档另做）：

- 父子关系必须能在 `taxonomy-v3.yaml` 解析。解析失败则 400，不得生成 `03_业务分类` 路径。旧 25 类编码在二级 ID 冻结前可以留下结果行，但不得生成正式 27 目录归档。
- 新的 `IRRELEVANT` 不生成 LV04 归档决策。低分或未说明确认无匹配的，进入 `NEED_REVIEW`。LV04 只由内部相关性门控在确认无匹配后写入。
- `CLASSIFIED` 只有在调用方已经完成校准门槛时，才允许随后生成 `archive_type=BUSINESS` 的决策。本接口不知道阈值是否校准，不得自行把分数当成通过。
- 结果行与任务状态要放在同一个事务。已有是两次提交。
- 同一 `file_id` 加决策版本重复提交时返回已有 `id`。已有每次都插入新行，不是幂等的。
- 请求中的 `file_hash` 不得写入 `source_sha256`。`source_sha256` 只接受 64 位小写文件字节哈希，可空、非唯一。
- 新决策行必须记下所依据的 `content_version`。该数是源字节版本，与决策 `version` 不是同一个数。04 第 7、9 表的现有列清单没有 `content_version`，补列前不得用决策 `version` 填它。

**数据库**：已有写 `classification_results`，可能更新 `doc_tasks`。计划在同一事务写 `archive_decisions` 版本 1，专利和低价值不走本接口的 `CLASSIFIED` 分支。

**Redis**：已有不投递。计划只在 `archive_decisions` 提交成功后投入 `archive_tasks`，消息含 `file_id`、决策 `version` 和该决策所依据的 `content_version`。

**状态与事务**：已有任务若结果属于五态终态，则 `doc_tasks.status=DONE`。这只表示结果已保存，不是 `archive_status=COMPLETED`。

**错误**：400 为 `invalid result_type`、`CLASSIFIED requires level1+level2`，或 `{type} must not carry categories`。401。

**幂等与测试**：已有不幂等。测试保持：合法 `CLASSIFIED` 返回 201；`MANUAL_REVIEW` 带 `level1` 返回 400；`IRRELEVANT` 不带类别返回 201，且不产生 LV04 归档行。

### H7 POST /review/{id}【已有】

提交人工复核。路径 `{id}` 是结果行 ID，不是 `file_id`。

## B. 九个内部模块接口

调用方向：Scheduler 消费 `pdf_tasks` 后调用 1～8；决策提交后再调用第 9 项。HTTP 不直接调用 PatentGate 或 Archive 复制。

**计划**（处理队列）：`pdf_tasks` 消息带 `file_id`、`task_id`、`content_version`。Worker 开始处理前，把消息中的 `content_version` 与 `file_registry` 当前 `content_version`（即 `file_content_versions` 中该文件已提交的最大版本）比较。两边都为空不是更旧。消息版本严格更旧则丢弃，不写决策、不复制。提交阶段结果时，更新条件带上开始时看到的 `content_version`；影响行数为 0 则丢弃，不写新决策行。内容从 N 升到 N+1（N≥1）时，非 `SCAN` 任务改为 `PENDING`、`retry=0`，错误列为空，`task_id` 不变，任务上的 `content_version` 改为 N+1。`SCAN` 只改 `content_version`。首次确认哈希写成版本 1 时，不把非 `SCAN` 打回 `PENDING`。

## C. 分类结果到真实复制再到 COMPLETED

1. **形成决策，而不是只形成分类行。** 专利写 `exclusion_decisions` 和 `archive_decisions(archive_type=PATENT)`，不要求 `classification_results` 有二级场景。低价值同样不要求业务二级。只有确认相关且父子合法，才写 `BUSINESS` 和 27 场景目录。证据不足写 `PENDING`，决策状态为 `NEED_REVIEW`。
2. **投递。** `archive_decisions` 提交成功后，向 `archive_tasks` 推送 `file_id`、决策 `version` 和该决策所依据的 `content_version`。Redis 不放 PDF。**已有** `RedisQueue` 用 `task_id` 做永久 `seen`，同一 ID 失败后不能再入队。这是当前实现缺口，不是登记幂等。计划改为：同一 `file_id` 加决策 `version` 在未完成时可以再次入队；该版本已经 `COMPLETED` 则不再复制；更旧的决策 `version` 直接丢弃。源文件当前 `content_version` 大于决策所依据的 `content_version` 时，不得写成 `COMPLETED`，也不得覆盖新内容。
3. **复制与校验。** Worker 用 `target_dir` 得到相对目录，不接受模型或请求体里的自由路径。只读源，临时文件与目标同一文件系统，流式复制。比对字节数、目标 SHA-256 和源指纹未变，再原子替换。文件名算法 TBD。
4. **回写。** 三个校验布尔值和 `final_path`、`completed_at` 在同一 PostgreSQL 事务提交后，`status` 才是 `COMPLETED`。事务失败则重新入队，不得把未提交当成成功。进程崩溃后若最终文件已在且校验通过，只补记 `COMPLETED`。
5. **复核重归档。** H7 计划路径把版本加 1。新文件校验成功后，旧执行改为 `SUPERSEDED`，与新行的 `COMPLETED` 同一事务，保证一个 `file_id` 只有一个 `COMPLETED` 主归档。不删除源 PDF。旧副本是否物理删除未批准，默认保留并标废弃。
6. **目录。** `BUSINESS` 必须是 `03_业务分类/{一级目录名}/{二级目录名}/`。专利、五类低价值、待复核不得写入这 27 个目录。
