# 900万PDF文档智能解析与两级分类系统技术实施

900万PDF文档智能解析与两级分类系统

版本：V1.0    日期：2026年10月

# 一、方案摘要

本方案不是单纯的OCR项目，而是一套面向海量历史PDF的智能文档治理方案。 系统直接读取服务器现有PDF，不迁移、不复制原始文件；根据文档是否存在文本层、是否为扫描件、版式是否复杂，自适应选择 PyMuPDF、PaddleOCR 或 MinerU 完成解析；再根据文档实际可用证据，动态选择“标题、正文、OCR文字、视觉内容”作为分类依据。

# 二、项目目标与边界

直接读取现有服务器上的PDF文件，不建设新的PDF文件存储系统。

自动识别文本PDF、扫描PDF、复杂版式PDF、纯图片PDF等不同类型。

恢复主标题、一级标题、二级标题、目录、正文段落等文档结构。

按照既定一级分类、二级分类体系进行智能分类。

允许输出“无关文件”和“待人工复核”，不强制每份文件必须落入某一类别。

保存分类结果、分类依据、模型分数、任务状态和异常信息，支持追溯与复盘。

# 四、PDF解析技术方案

## 4.1 文本型PDF：PyMuPDF

对于本身具有可靠文本层的PDF，直接使用PyMuPDF提取文本和版面信息，不做OCR。重点保留：

页文本

字体大小与字体样式

文字坐标BBox

页码

段落位置

粗体/字号等标题判断特征

## 4.2 普通扫描PDF：PaddleOCR

对于扫描形成、内部没有文本层的PDF，按页转图片后进行OCR。OCR结果不能只保留纯文本，必须同时保留坐标、页码和识别置信度，为后续标题结构识别提供基础。

## 4.3 复杂版式PDF：MinerU

仅当文档存在多栏、复杂图文混排、表格密集、阅读顺序混乱、标题层级复杂等情况时，才进入MinerU进行结构化解析。

图片区域识别

# 五、Evidence Router：多证据自适应分类

实际历史文档并不总有清晰标题。系统不能把“标题优先”理解成“没有标题就失败”，而应根据可用证据自动路由。

# 六、标题结构与标题信息量判断

主标题和各级正文标题是分类的第一优先证据，因为它们本质上是文档作者对主题进行过的人工作业概括。但并不是所有标题都具有分类价值。

Title Information Score主要依据：领域词、核心业务对象、业务动作、标题长度、章节标题数量、是否为泛化表达等进行判断。该分值主要用于路由，不建议简单理解成固定“标题80%+正文20%”的数学权重。

# 七、分类知识库建设

当前没有成熟人工标注训练集，因此一期分类准确率的基础不是“训练一个模型”，而是把现有一级、二级目录建设成可被机器理解的分类知识库。

# 八、Relevance Gate：先判断是否属于现有分类体系

海量历史文档中一定存在不属于现有一级/二级目录的材料。如果直接进入分类模型，系统会被迫把无关文件“硬塞”进某个类别。因此必须在一级分类前增加开放集相关性判断。

判断依据综合考虑：BGE-M3最高相似度、Top1与Top2差值、领域词命中、规则命中、Evidence Mode。正式阈值不拍脑袋设定，而通过真实样本校准。

# 九、一级分类技术实现

一级类别数量有限，采用“规则辅助 + BGE-M3语义匹配 + 疑难LLM裁决”的轻量方式即可。一级通常不需要Reranker。

# 十、二级分类技术实现

一级确定后，只加载该一级下面的二级类别，避免所有二级类别全局竞争。二级分类是准确率控制的关键环节。

# 十一、正文关键段落抽取与结果校验

正文不是随机取前几段，也不是把全文全部送给模型。对标题缺失或候选接近的文件，采用“候选驱动正文检索”。

分类完成后再做正文一致性检查。例如模型判断“危险化学品监管”，但高相关正文全部讨论“煤矿、尾矿库、矿井”，则判定分类证据冲突，不自动归档，进入人工复核。

# 十二、纯图片与视觉模式处理

对于OCR有效文本极少的纯图片PDF，采用视觉理解模型生成“事实描述”，再进入相关性判断和两级分类。例如：

VISION_MODE的自动通过阈值应高于普通文本模式。图片模糊、证据不足时优先进入MANUAL_REVIEW。

# 十四、结果数据与存储策略

原始PDF继续存放在现有服务器，系统不保存PDF副本，仅保存轻量化处理结果。

生产环境建议使用PostgreSQL保存结果和任务状态；小规模验证阶段也可以先输出CSV/Excel。

# 十五、900万规模任务调度与可靠性

900万份文件不能采用单进程顺序处理，需要任务队列和Worker并行处理。

每个处理阶段独立记录状态，失败只重跑当前阶段。

支持断点续跑，系统重启后不重复处理已完成文件。

OCR、MinerU、Embedding、Reranker可按资源类型分别部署CPU/GPU Worker。

对异常PDF、加密PDF、损坏PDF建立独立异常队列。

# 十九、本方案体现的关键技术工作与项目价值

本方案的工作重点并非简单组合若干开源工具，而是针对900万份历史文档的真实复杂性，对整个处理链路进行系统设计和风险收敛。主要工作成果包括：

从“所有PDF统一OCR”优化为文本、扫描、复杂版式分流解析，显著降低不必要的计算成本。

从“标题优先”进一步完善为Evidence Router，多证据自适应处理无标题、纯正文、扫描、纯图片等真实场景。

引入Open-set思想，在一级分类前增加Relevance Gate，使系统具备“无关文件”拒识能力，避免强制错分。

将二级分类设计为BGE召回+Reranker精排+LLM疑难裁决的级联架构，兼顾吞吐量、准确率和模型成本。

明确正文仅在标题信息不足或候选冲突时参与，并采用候选驱动段落检索而非简单全文分类，降低正文噪声。

建立CLASSIFIED、IRRELEVANT、MANUAL_REVIEW、FAILED四类最终状态，使系统具备生产环境所需的容错与可运营性。

通过分类知识库沉淀类别定义、业务对象、业务动作、排除边界，为后续监督学习和模型持续优化建立数据资产。

# 二十、硬件资源评估原则

900万份PDF的硬件规模不能只按“文件数量”估算，真正决定资源规模的是总页数、扫描件比例、复杂版式比例、纯图片比例、计划完成周期以及是否私有化部署LLM/Vision。

按上述预算级假设，对应处理量约为：文本解析4500万页、OCR约3150万页、MinerU约900万页、视觉类约450万页。该比例仅用于形成初步预算，不作为最终采购依据。
