# 900万PDF智能处理系统硬件配置评估报告

900万PDF智能处理系统

硬件配置评估报告

单服务器一体化部署 · 3个月处理目标

说明：本报告给出预算级、生产级硬件建议。最终“三个月工期”承诺应以真实PDF样本Benchmark结果校准。

# 一、执行摘要

本项目需要在单台物理服务器上完成约900万份PDF的解析、OCR、复杂版式识别、Embedding、Reranker、疑难LLM/Vision判定、任务调度及结果存储。与普通业务系统不同，本项目既包含大量CPU密集型任务，也包含持续GPU推理任务，因此硬件必须采用“高核CPU + 大内存 + 多GPU + 高速NVMe”的一体化设计。

如果仅要求“系统可以运行”，2张48GB GPU即可完成完整技术链路；但如果目标是“3个月内完成900万份历史PDF首轮全量处理”，建议采用更保守的生产保障型配置，并通过真实数据Benchmark校准最终吞吐。

# 二、评估前提与容量基线

为便于做预算级估算，本报告采用以下基线。该基线不是对现有900万份PDF真实分布的断言，正式采购前需要通过1万份样本进行校准。

按上述基线，总工作量约为9000万页。90天完成意味着全链路平均每天约处理100万页，约11.6页/秒。考虑I/O等待、异常文件、重试、模型切换、维护及资源利用率后，建议把系统设计能力按16～18页/秒以上进行容量校验。

# 三、为什么需要这样的硬件配置

## 3.1 CPU：64～96物理核心

本项目不是单纯GPU项目。目录扫描、PDF打开、文件类型判断、PyMuPDF文本解析、PDF页面渲染、图像预处理、标题识别、段落切分、规则判断、数据库写入等工作主要由CPU完成。

单机情况下CPU还需要同时支撑FastAPI、Redis、PostgreSQL及多进程Worker。若CPU核心数不足，常见结果是GPU处于空闲等待状态，整体速度并不会因为GPU很强而提升。

因此建议64核起步，预算允许时采用96核，以便同时运行16～32个Parser Worker并为GPU持续准备任务。

## 3.2 内存：512GB ECC

如果只有一台服务器，操作系统、数据库、Redis、Parser Worker、PaddleOCR、MinerU、BGE、Reranker及LLM/Vision可能同时常驻。256GB可以运行，但在长时间高并发下余量有限。

512GB ECC可以显著降低频繁换页、OOM和多模型争抢内存的风险，更适合三个月持续批处理。

## 3.3 GPU：4张48GB

GPU是整个项目的核心推理资源。PaddleOCR、MinerU、BGE-M3、Reranker以及Vision/LLM都可能使用GPU。

4张48GB卡的价值不只是总显存，更重要的是可以并行执行不同阶段任务，避免OCR、MinerU和LLM互相抢占同一张卡。

## 3.4 NVMe：4～8TB高速工作盘

900万份原始PDF不需要迁移到本机，原文件仍保留在现有服务器。NVMe工作盘主要用于PDF转图片、OCR临时文件、MinerU中间文件、模型缓存、批处理缓存和失败重试文件。

4TB通常可以作为起点；如果中间文件保留时间较长或页面分辨率较高，8TB更稳妥。处理完成后的临时文件应自动清理。

## 3.5 网络：10GbE起步，25GbE按需

如果原始PDF在另一台文件服务器/NAS上，计算服务器会持续跨网络读取文件。网络过慢时，GPU会等待I/O。

因此建议10GbE起步；如果现有存储端也支持更高带宽，并且Benchmark显示网络成为瓶颈，再升级到25GbE。若PDF就在本机，则25GbE不是必须项。

# 四、单服务器内部资源分工

单台物理服务器并不意味着所有任务串行运行。系统仍应采用“主控调度 + 多Worker流水线 + GPU并行”的方式运行。

当某一队列积压时，可动态调整GPU角色。例如OCR任务过多时，GPU 2也可临时加入OCR；复杂PDF较少时，GPU 2可参与Embedding/Reranker或Vision推理。

# 五、三个月工期的容量测算逻辑

容量规划核心公式为：

所需资源 ≈ 总工作量 ÷ 单节点实测吞吐 ÷ 可用时间 × 冗余系数

按900万份、平均10页估算，总量约9000万页。90天完成，则全链路平均每天约100万页。为了避免按100%资源利用率做危险设计，建议以70%～75%的有效利用率进行校核。

OCR容量示例

若扫描件约占35%，OCR工作量约3150万页。90天平均约35万页/天，即约4.05页/秒。按70%有效利用率折算，OCR子系统建议具备约5.8页/秒以上的稳定能力。双48GB GPU并行OCR能够提供更充分的冗余空间，但最终仍应以真实PaddleOCR Benchmark为准。

MinerU容量示例

若复杂版式约占10%，MinerU工作量约900万页。90天平均约10万页/天，即约1.16页/秒。考虑利用率后，复杂版式链路建议具备约1.6页/秒以上的稳定能力。若真实复杂文档比例显著低于10%，MinerU压力会大幅下降。

# 八、建议的软件与运行环境

操作系统：Ubuntu Server 22.04/24.04 LTS；

容器：Docker / Docker Compose，用于隔离OCR、MinerU、Embedding和业务服务；

任务调度：Redis + Celery，单机场景优先于Kafka，结构更简单；

数据库：PostgreSQL，保存任务状态、分类结果、错误信息及处理日志；

监控：Prometheus + Grafana 或轻量系统监控，重点观察CPU/GPU利用率、显存、队列积压、磁盘I/O和失败率；

GPU运行：CUDA版本根据GPU型号及Paddle/MinerU依赖统一锁定，避免运行时版本冲突。

# 九、正式采购/上线前必须做的Benchmark

“3个月内一定跑完”不能只依据理论配置承诺。最专业的方式是在目标服务器上抽取1万份真实PDF做压力测试，并记录以下指标：

平均页数

文本/扫描/复杂/纯图片比例

PyMuPDF页/秒

PaddleOCR页/秒/GPU

MinerU页/秒/GPU

BGE/Reranker文档/秒

LLM/Vision实际调用比例

CPU平均利用率和峰值

GPU平均利用率、显存峰值

NVMe读写吞吐

异常/重试比例

建议把“三个月工期”的技术验收线定义为：在真实样本长时间压力测试下，系统综合吞吐稳定达到16～18页/秒以上，且OCR/MinerU任务队列不持续增长、CPU长期不超过85%、内存不发生频繁Swap、GPU无持续OOM。满足该条件后，再对900万全量工期进行正式确认。

# 十一、最终建议

推荐采购/部署基线：

服务器：1台高性能GPU计算服务器

CPU：64～96物理核心，服务器级处理器

内存：512GB ECC

GPU：4 × 48GB NVIDIA GPU

系统盘：1TB 企业级NVMe

高速工作盘：4～8TB 企业级NVMe

网络：10GbE起步；跨服务器读取PDF且存储端支持时推荐25GbE

操作系统：Ubuntu Server LTS

部署方式：单服务器，多Worker流水线并行

管理层结论：

在单服务器约束下，为兼顾900万份PDF全量处理、3个月工期目标和后续持续运行，建议按64～96核CPU、512GB内存、4张48GB GPU及4～8TB NVMe高速工作盘进行生产级规划。该配置属于“工期保障型预算配置”，不是最终绝对值。正式采购前必须以1万份真实PDF进行Benchmark，并以综合吞吐达到16～18页/秒以上作为三个月工期的容量校验依据。

# 附录：领导快速问答

为什么不是普通业务服务器？

因为本项目同时包含大规模PDF解析、OCR、复杂版式识别和AI推理，需要持续高CPU与GPU并发。

为什么要4张GPU？

不是所有卡都跑同一个模型，而是让OCR、MinerU、分类和Vision/LLM并行，减少相互等待。

8TB NVMe是不是保存900万PDF？

不是。原PDF继续存放在现有服务器，NVMe主要作为高速临时工作区；4TB也可以作为起点。

25GbE是不是必须？

不是。10GbE可以起步；只有跨服务器读取文件且I/O成为瓶颈时才建议升级25GbE。

能不能保证3个月？

硬件配置可以按3个月目标设计，但正式承诺必须以真实PDF Benchmark为依据。

以后还能扩吗？

单机可以先通过增加Worker和动态GPU调度优化；若工期进一步压缩，则需要增加GPU或扩展为多节点。
